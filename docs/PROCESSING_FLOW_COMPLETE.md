# 播客处理完整流程说明

## 📊 正常处理流程（大部分播客）

### 流程概览

```
播客链接
  ↓
ASR转写（整体处理，按120秒分段）
  ↓
生成总结报告（generateReportWhole）
  ↓
检查输入长度
  ├─ 如果 totalInputTokens > 900,000 tokens
  │   └─ → 分块处理（generateReportChunked）
  │
  └─ 如果 totalInputTokens ≤ 900,000 tokens ✅ 正常流程
      ↓
      判断段落数
      ├─ 如果 segments.length ≤ 40
      │   └─ → 单轮生成（generateReportWholeFallback）
      │       ├─ 成功 → 返回总结 ✅
      │       └─ 失败（内容审核错误等）
      │           └─ → 分块处理（generateReportChunked）
      │
      └─ 如果 segments.length > 40
          └─ → 两轮生成（大纲+填充）
              ├─ 第一轮：生成大纲
              │   ├─ 成功 → 继续
              │   └─ 失败 → 回退到单轮生成
              │
              └─ 第二轮：基于大纲+ASR生成报告
                  ├─ 成功 → 返回总结+大纲 ✅
                  └─ 失败（内容审核错误等）
                      └─ → 回退到单轮生成
                          ├─ 成功 → 返回总结 ✅
                          └─ 失败 → 分块处理（generateReportChunked）
```

### 正常流程详细说明

#### 1. 单轮生成（segments ≤ 40）

**触发条件**：
- 输入长度 ≤ 900,000 tokens
- ASR分段数 ≤ 40

**处理方式**：
- 直接基于ASR原文生成完整报告
- 使用 `generateReportWholeFallback` 函数
- 一次性调用LLM API，生成完整报告

**成功路径**：
```
generateReportWholeFallback
  ↓
调用 qwenChat（maxTokens: 32,000）
  ↓
返回 summary ✅
```

**失败路径**：
```
generateReportWholeFallback
  ↓
遇到内容审核错误
  ↓
调用 generateReportChunked（分块处理）
```

#### 2. 两轮生成（segments > 40）

**触发条件**：
- 输入长度 ≤ 900,000 tokens
- ASR分段数 > 40

**处理方式**：
- 第一轮：生成详细大纲/框架
- 第二轮：基于大纲+原始ASR生成完整报告

**成功路径**：
```
第一轮：生成大纲
  ↓
调用 qwenChat（生成大纲）
  ↓
第二轮：基于大纲+ASR生成报告
  ↓
调用 qwenChat（maxTokens: 32,000）
  ↓
返回 summary + outline ✅
```

**失败路径**：
```
第一轮失败
  ↓
回退到单轮生成（generateReportWholeFallback）
  ↓
如果单轮也失败 → 分块处理（generateReportChunked）
```

## 🔀 分块处理流程（备用方案）

### 触发条件

#### 1. 输入长度超限（自动触发）
- **条件**：`totalInputTokens > 900,000 tokens`
- **计算方式**：
  - `estimatedTokens = transcript.length`（中文约1字符=1token）
  - `totalInputTokens = estimatedTokens + 10,000`（提示词）
- **触发场景**：超长播客（ASR原文 > 890,000字符）
- **频率**：很少（大部分播客ASR原文在10万-20万字符）

#### 2. 内容审核错误（回退触发）
- **条件**：单轮/两轮生成遇到内容审核错误
- **错误信息**：`data_inspection_failed` 或 `inappropriate content`
- **触发场景**：ASR原文或大纲触发了API的内容安全机制
- **频率**：偶尔（取决于播客内容）

#### 3. API限制错误（回退触发）
- **条件**：遇到输入/限制相关的错误
- **错误信息**：包含 `输入`、`input`、`limit`、`限制` 等关键词
- **触发场景**：API返回限制相关的错误
- **频率**：很少

### 分块处理详细流程

```
generateReportChunked
  ↓
分块策略选择
  ├─ 如果有ASR分段（segments）
  │   └─ → 使用ASR原有分段（保持语义边界）
  │       ├─ 如果段数 ≤ 100：直接使用
  │       └─ 如果段数 > 100：合并相邻段（目标100段左右）
  │
  └─ 如果没有segments（降级策略）
      └─ → 按固定字符数切割
          - 块大小：4000字符
          - 重叠：500字符
  ↓
逐个处理每个块（测试阶段）
  ├─ 对每个块调用LLM API（maxTokens: 10,000）
  ├─ 记录成功和失败的块索引
  ├─ 每个块最多处理5分钟（超时则跳过）
  └─ 显示进度日志（如：块 5/47 (10.6%)）
  ↓
计算成功率
  ↓
判断是否满足优化条件
  ├─ 成功率 ≥ 80%？
  ├─ 有原始ASR分段（segments）？
  └─ 合并后的ASR片段长度在限制内？
  ↓
如果满足优化条件：
  ↓
合并成功的ASR片段
  ↓
使用合并后的ASR片段走整体处理逻辑
  ├─ 调用 generateReportWhole（fromChunked=true）
  ├─ 使用单轮或两轮生成（根据段数决定）
  └─ 如果成功 → 返回结果 ✅
  ↓
如果失败或不满足条件：
  └─ → 回退到分块处理+整合逻辑
      ↓
      合并所有块的摘要
      ↓
      如果块数 > 1：
        └─ → 调用LLM进行最终整合（maxTokens: 32,000）
            ├─ 成功 → 返回整合后的报告 ✅
            └─ 失败 → 使用合并结果作为最终报告 ✅
      ↓
      如果块数 = 1：
        └─ → 直接返回该块的摘要 ✅
```

### 分块处理的关键特性

1. **进度日志**：显示每个块的处理进度和耗时
2. **超时机制**：每个块最多处理5分钟，超时则跳过
3. **智能优化**：如果成功率 ≥ 80%，尝试合并成功的ASR片段走整体处理
4. **自动回退**：如果整体处理失败，自动回退到分块处理+整合逻辑
5. **避免递归**：使用 `fromChunked` 标志，避免无限递归

## ✅ 所有路径的完成保证

### 正常流程完成保证

1. **单轮生成路径**：
   - ✅ 成功：直接返回总结
   - ✅ 失败：回退到分块处理（保证完成）

2. **两轮生成路径**：
   - ✅ 第一轮成功 + 第二轮成功：返回总结+大纲
   - ✅ 第一轮失败：回退到单轮生成（保证完成）
   - ✅ 第二轮失败：回退到单轮生成（保证完成）
   - ✅ 单轮也失败：回退到分块处理（保证完成）

### 分块处理完成保证

1. **优化策略路径**：
   - ✅ 成功率 ≥ 80%：尝试整体处理
     - 成功：返回结果
     - 失败：回退到分块处理+整合（保证完成）

2. **分块处理+整合路径**：
   - ✅ 所有块都失败：抛出错误（有明确错误信息）
   - ✅ 部分块成功：
     - 如果块数 = 1：直接返回该块的摘要
     - 如果块数 > 1：尝试整合
       - 整合成功：返回整合后的报告
       - 整合失败：使用合并结果作为最终报告（保证完成）

### 错误处理保证

1. **递归保护**：
   - ✅ 使用 `fromChunked` 标志，避免无限递归
   - ✅ 如果从分块处理调用，遇到错误直接抛出，不会再次调用分块处理

2. **超时保护**：
   - ✅ 每个块最多处理5分钟
   - ✅ 整体处理有动态超时机制（60-120分钟）

3. **部分结果保护**：
   - ✅ 如果部分块成功，会使用成功的块生成报告
   - ✅ 如果整合失败，会使用合并结果作为最终报告

## 📊 流程总结

### 正常流程（大部分播客）

- **输入长度**：≤ 900,000 tokens
- **处理方式**：单轮或两轮生成
- **成功率**：高（大部分情况下）
- **处理时间**：几分钟到几十分钟

### 分块处理（备用方案）

- **触发条件**：
  1. 输入长度超限（很少）
  2. 内容审核错误（偶尔）
  3. API限制错误（很少）
- **处理方式**：
  1. 逐个处理每个块（测试阶段）
  2. 如果成功率 ≥ 80%，尝试整体处理（优化策略）
  3. 否则，合并所有块的摘要并整合
- **成功率**：高（即使部分块失败，也能生成报告）
- **处理时间**：较长（取决于块数和每个块的处理时间）

### 完成保证

✅ **所有路径都能正常完成**：
- 正常流程：单轮或两轮生成，成功率高
- 分块处理：即使部分块失败，也能生成报告
- 错误处理：有明确的回退机制和错误信息
- 递归保护：避免无限递归
- 超时保护：避免长时间卡住
