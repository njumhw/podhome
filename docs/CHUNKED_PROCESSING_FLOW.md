# 分块处理（Chunked Processing）详细流程

## 📋 分块处理的完整流程

### 第一步：分块策略选择

```
输入：ASR原文（transcript）和ASR分段（segments）
  ↓
判断是否有ASR分段
  ├─ 如果有 segments（优先使用）
  │   └─ → 使用ASR原有分段（保持语义边界）
  │       ├─ 如果段数 ≤ 100：直接使用
  │       └─ 如果段数 > 100：合并相邻段（目标100段左右）
  │
  └─ 如果没有 segments（降级策略）
      └─ → 按固定字符数切割
          - 块大小：4000 字符
          - 重叠：500 字符
          - 可能破坏语义边界
```

**示例**：
- **有ASR分段**：92分钟播客 → 约73段（每段120秒）→ 直接使用73段
- **无ASR分段**：97,445字符 → 约24块（4000字符/块，500字符重叠）

---

### 第二步：逐个块处理（测试阶段）

```
对每个块（chunk）：
  ↓
1. 构建提示词
   - 系统提示词：从数据库获取（report_generation_whole）
   - 用户提示词：要求详细展开，目标长度20-30%
  ↓
2. 调用LLM API
   - maxTokens: 10,000（已从2,500提升）
   - temperature: 0.1
  ↓
3. 处理结果
   ├─ 成功 → 保存到 reportChunks 数组，记录成功块的索引
   └─ 失败 → 记录错误，跳过该块（继续处理其他块）
```

**关键配置**：
- **每个块的maxTokens**：10,000 tokens（允许生成更详细的摘要）
- **提示词要求**：详细展开，不要只列观点标题
- **目标长度**：每个块的摘要应达到输入内容的20-30%

**错误处理**：
- 如果某个块遇到内容审核错误：跳过该块，继续处理其他块
- 如果所有块都失败：抛出错误

**记录信息**：
- 记录每个成功块的索引（`successfulChunkIndices`）
- 计算成功率：`successRate = successfulChunkIndices.length / chunks.length`

---

### 第三步：智能优化策略（新增）

```
计算成功率
  ↓
判断是否满足优化条件：
  ├─ 成功率 ≥ 80%？
  ├─ 有原始ASR分段（segments）？
  └─ 合并后的ASR片段长度在限制内？
  ↓
如果满足：
  ↓
合并成功的ASR片段
  ↓
使用合并后的ASR片段走整体处理逻辑
  ├─ 调用 generateReportWhole()
  ├─ 使用单轮或两轮生成（根据段数决定）
  └─ 如果成功 → 返回结果 ✅
  ↓
如果失败或不满足条件：
  └─ → 回退到分块处理+整合逻辑
```

**优化条件**：
- **最低成功率阈值**：80%（可配置 `MIN_SUCCESS_RATE = 0.8`）
- **必须有原始ASR分段**：`originalSegments` 存在且长度 > 0
- **合并后长度限制**：总输入Token ≤ 900,000

**优势**：
- ✅ **质量提升**：整体处理的质量通常比分块处理+整合更好
- ✅ **语义连贯**：一次性处理，保持语义连贯性
- ✅ **避免信息丢失**：减少分块处理的信息丢失和整合质量问题
- ✅ **智能回退**：如果整体处理失败，自动回退到分块处理+整合逻辑

**示例**：
- 28个块，27个成功（成功率 96.4%）
- 合并27个成功的ASR片段
- 使用整体处理逻辑生成报告
- 如果整体处理失败，回退到分块处理+整合逻辑

---

### 第四步：合并所有块的结果（回退路径）

```
如果优化策略未使用或失败，执行此步骤：
  ↓
合并所有成功的块摘要
  ↓
combinedReport = reportChunks.join('\n\n')
```

**示例**：
- 如果处理了28个块，每个块生成2000字符的摘要
- 合并后：combinedReport = 约56,000字符

---

### 第五步：最终整合（如果块数 > 1，回退路径）

```
如果 reportChunks.length > 1：
  ↓
调用LLM进行最终整合
  ↓
输入：combinedReport（所有块的摘要）
  ↓
提示词要求：
  - 充分展开而非压缩
  - 保持逻辑连贯
  - 删除重复内容（但不过度压缩）
  - 目标长度：达到原始内容的20-30%
  - 充分利用32K token上限
  ↓
输出：finalSummary（最终报告）
```

**关键配置**：
- **maxTokens**：32,000 tokens（充分利用输出上限）
- **提示词要求**：充分展开而非压缩，目标长度20-30%

**如果整合失败**：
- 使用合并结果（combinedReport）作为最终报告

---

## 🔍 具体示例：92分钟播客的分块处理

### 输入数据
- **ASR原文**：97,445 字符
- **ASR分段**：73段（每段约120秒）
- **触发原因**：内容审核错误（回退机制）

### 处理流程

#### Step 1: 分块策略
```
✅ 使用ASR原有分段: 73 段（保持语义边界）
→ 直接使用73段，不合并（因为 < 100）
```

#### Step 2: 逐个块处理
```
块 1/73: 处理成功，长度: 2,100 字符
块 2/73: 处理成功，长度: 1,950 字符
块 3/73: 处理成功，长度: 2,050 字符
...
块 12/73: 遇到内容审核错误，跳过该块
块 13/73: 处理成功，长度: 1,980 字符
...
块 28/73: 处理成功，长度: 2,000 字符
```

**结果**：
- 成功处理：27个块
- 失败跳过：1个块（内容审核错误）
- 每个块平均长度：约2,000字符

#### Step 3: 合并结果
```
combinedReport = 27个块的摘要合并
→ 总长度：约54,000字符
```

#### Step 4: 最终整合
```
输入：combinedReport（54,000字符）
  ↓
LLM整合（maxTokens: 32,000）
  ↓
输出：finalSummary（最终报告）
```

**问题**：
- 如果最终整合的提示词过于简单（只要求"保持逻辑连贯、删除重复"）
- LLM可能会过度压缩，导致最终报告过短
- **已修复**：改进提示词，要求充分展开而非压缩

## ⚠️ 分块处理的问题（已修复）

### 问题1：每个块的maxTokens过低
- **原配置**：2,500 tokens
- **问题**：每个块的摘要过短，无法充分展开
- **修复**：提升到 10,000 tokens

### 问题2：分块提示词过于简单
- **原提示词**：`请基于以下播客内容片段生成报告摘要`
- **问题**：没有要求详细展开，导致摘要过短
- **修复**：要求详细展开，目标长度20-30%

### 问题3：最终整合提示词过于简单
- **原提示词**：`保持逻辑连贯、删除重复内容`
- **问题**：LLM会过度压缩，导致最终报告过短
- **修复**：要求充分展开而非压缩，目标长度20-30%

## 📊 分块处理 vs 整体处理对比

| 维度 | 整体处理 | 分块处理（原逻辑） | 分块处理（优化后） |
|------|---------|------------------|-------------------|
| **触发条件** | 默认（大部分播客） | 输入超限/内容审核错误 | 输入超限/内容审核错误 |
| **处理方式** | 一次性处理整个ASR原文 | 分块处理，然后整合 | 先测试块，如果成功率高则合并走整体处理 |
| **语义完整性** | ✅ 完整 | ⚠️ 可能丢失跨块语义 | ✅ 优化后保持完整（如果使用整体处理） |
| **处理速度** | 较快（1次API调用） | 较慢（N+1次API调用） | 中等（N次测试 + 1次整体处理） |
| **内容审核风险** | 较高（一次性发送大量内容） | 较低（每个块较小） | 较低（测试阶段识别问题块） |
| **报告质量** | ✅ 通常更好 | ⚠️ 取决于整合质量 | ✅ 优化后质量更好（如果使用整体处理） |
| **适用场景** | 大部分播客 | 超长播客/内容审核错误 | 超长播客/内容审核错误（但成功率高的场景） |
| **智能回退** | N/A | N/A | ✅ 如果整体处理失败，自动回退到分块处理+整合 |

- ✅ 提高每个块的maxTokens（2,500 → 10,000）
- ✅ 改进分块提示词（要求详细展开）

### 2. 最终整合优化（已完成）
- ✅ 改进整合提示词（要求充分展开而非压缩）
- ✅ 明确目标长度（20-30%）

### 3. 智能优化策略（已完成）✨
- ✅ **成功率检测**：记录每个块的处理结果，计算成功率
- ✅ **智能合并**：如果成功率 ≥ 80% 且有原始ASR分段，合并成功的ASR片段
- ✅ **整体处理优先**：使用合并后的ASR片段走整体处理逻辑（单轮或两轮生成）
- ✅ **自动回退**：如果整体处理失败，自动回退到分块处理+整合逻辑
- ✅ **质量提升**：整体处理的质量通常更好，保持语义连贯性

### 4. 未来优化方向
- 考虑对ASR原文进行预处理，降低内容审核风险
- 优化成功率阈值（当前80%），根据实际效果调整
- 监控分块处理的成功率，识别问题模式
- 考虑对失败的块进行重试或特殊处理

## 📝 总结

**分块处理流程**：
1. **分块**：优先使用ASR分段，保持语义边界
2. **处理**：逐个块生成详细摘要（maxTokens: 10,000）
3. **合并**：合并所有块的摘要
4. **整合**：最终整合成完整报告（maxTokens: 32,000）

**关键改进**：
- ✅ 提高每个块的maxTokens
- ✅ 改进分块和整合的提示词
- ✅ 要求充分展开而非压缩

**适用场景**：
- 输入长度超限（很少）
- 内容审核错误（偶尔）← 这个播客的情况
- API限制错误（很少）
