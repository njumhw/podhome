# 待讨论的业务问题

## 一、核心业务逻辑

### 1. Reader 升级为 Podcaster 的入口设计
**问题**: Reader 想要升级为 Podcaster 时，应该在哪里触发升级流程？

**方案 A（推荐）**: 点击上传按钮时
- 优点：用户意图明确，在需要时触发
- 缺点：用户可能不知道需要升级

**方案 B**: 个人中心页面
- 优点：用户可以主动查看和升级
- 缺点：可能被忽略

**方案 C**: 两者都提供
- 优点：覆盖更多场景
- 缺点：需要维护两处入口

**建议**: 采用方案 C，但以方案 A 为主入口。

---

### 2. 注册流程的改动
**当前状态**: 注册需要邀请码

**需要改动**:
- 移除注册表单中的邀请码字段
- 注册 API 不再验证邀请码
- 注册后默认角色为 `READER`
- 注册页面文案更新："注册即可获得 Reader 权限"

**问题**: 
- 是否需要保留"邀请码"字段但设为可选？
- 还是完全移除邀请码字段？

**建议**: 完全移除邀请码字段，简化注册流程。

---

### 3. 邀请码的生成和分发机制
**问题**: Podcaster 邀请码如何生成和分发？

**方案**:
- 管理员在后台生成邀请码
- 可以设置：
  - 最大使用次数（默认 1 次）
  - 过期时间（可选）
- 邀请码可以：
  - 通过后台查看和复制
  - 通过邮件/消息发送给用户
  - 公开分享（如果设置多次使用）

**问题**:
- 是否需要记录邀请码的使用者？
- 是否需要限制每个 Reader 只能使用一次邀请码？

**建议**: 
- 记录使用者信息，便于追踪
- 不限制使用次数（由邀请码的 maxUses 控制）

---

### 4. Podcaster-VIP 的授权标准
**问题**: 什么情况下应该授权用户为 Podcaster-VIP？

**可能的标准**:
- 上传数量达到阈值（如 50 个播客）
- 贡献度（点赞数、评论数）
- 管理员主观判断
- 特殊贡献（如优质内容、社区活跃）

**建议**: 
- 初期：完全由管理员主观判断
- 后期：可以设置自动化规则（如上传 50 个自动升级）

## 二、技术实现细节

### 5. AccessLog 表的字段扩展
**问题**: 需要在 `AccessLog` 表中添加哪些字段来支持 Visitor 访问计数？

**需要添加的字段**:
- `userIp`: String? - 用户 IP 地址
- `userAgent`: String? - 浏览器 User-Agent

**问题**:
- 是否需要为所有访问记录这些字段？
- 还是仅 Visitor 访问时记录？

**建议**: 
- 为所有访问记录 IP 和 User-Agent
- 登录用户的访问，userId 不为 null，IP/User-Agent 作为补充信息
- Visitor 的访问，userId 为 null，IP/User-Agent 作为主要标识

---

### 6. 数据库迁移的执行时机
**问题**: 何时执行用户角色迁移？

**方案 A**: 一次性迁移
- 在部署新版本时，执行数据库迁移脚本
- 所有现有 USER → PODCASTER
- 优点：简单直接
- 缺点：如果迁移失败，需要回滚

**方案 B**: 渐进式迁移
- 用户首次登录时自动迁移
- 优点：更安全，可以逐步验证
- 缺点：需要维护迁移状态

**建议**: 采用方案 A，在部署前先在测试环境验证。

---

### 7. 向后兼容性
**问题**: 现有代码中可能硬编码了 `USER` 角色，如何保证兼容性？

**需要检查的地方**:
- API 路由中的角色检查
- 前端组件中的角色判断
- 数据库查询中的角色过滤

**建议**:
- 全局搜索 `role === 'USER'` 和 `role === 'ADMIN'`
- 替换为新的角色枚举
- 添加角色常量定义，避免硬编码

## 三、用户体验优化

### 8. Visitor 限制提示的显示方式
**问题**: Visitor 访问限制的提示应该在哪里显示？

**方案 A**: 页面顶部固定提示条
- 优点：始终可见，提醒明确
- 缺点：可能遮挡内容

**方案 B**: 仅在详情页显示
- 优点：不干扰浏览
- 缺点：用户可能不知道限制

**方案 C**: 列表页 + 详情页都显示
- 优点：信息完整
- 缺点：可能过于频繁

**建议**: 采用方案 B，但在超过限制时显示明显的模态框。

**引导内容**:

- 注册成功后显示欢迎页面或提示

**建议**: 简化引导，仅在注册成功时显示简短提示。

### 10. VIP 授权的通知方式
**问题**: 用户被授权为 VIP 后，如何通知用户？

**方案 A**: 站内通知
- 用户下次登录时显示提示
- 优点：简单直接
- 缺点：用户可能不登录

**方案 B**: 邮件通知
- 发送邮件通知用户
- 优点：及时通知
- 缺点：需要邮件服务

**方案 C**: 两者结合

- 优点：覆盖全面

**建议**: 初期采用方案 A，后期可考虑方案 C。

## 四、边界情况处理

### 11. 同一网络下的 Visitor 限制
**问题**: 如果多个用户在同一网络（相同 IP），会共享 Visitor 限制吗？

**影响**:
- 公司/学校网络：多个用户共享 IP
- 家庭网络：多个设备共享 IP

**解决方案**:
- 使用 IP + User-Agent 组合识别
- 不同浏览器/设备会有不同的 User-Agent
- 但同一设备的多个标签页会共享限制

**建议**: 
- 接受这个限制（Visitor 本身就是低权限）
- 在提示中说明："同一网络下的用户可能共享限制"
- 引导用户注册以获得独立权限

---

### 12. 邀请码的重复使用
**问题**: 如果邀请码设置了多次使用，如何防止滥用？

**限制措施**:
- 每个用户只能使用一次邀请码升级
- 记录邀请码的使用者
- 检查用户是否已经升级过

**建议**: 
- 在升级 API 中检查用户当前角色
- 如果已经是 Podcaster 或更高，拒绝升级
- 记录升级历史，防止重复使用

---

### 13. 数据清理策略
**问题**: AccessLog 表会不断增长，如何清理旧数据？

**清理策略**:
- 保留最近 30 天的访问记录
- 定期清理过期记录（如每天凌晨）
- 或者按需清理（当表大小超过阈值时）

**建议**: 
- 实现定期清理任务
- 保留最近 30 天的记录用于分析
- 更早的记录可以归档或删除
